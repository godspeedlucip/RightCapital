# API 通知系统设计规格

## 1. 文档目标

本文档定义一个企业内部 HTTP(S) 通知服务的 MVP 设计，用于接收业务系统提交的外部通知请求，并以尽可能可靠的方式投递到供应商 API。

本设计服务于以下目标：

- 让业务系统不需要直接处理供应商 API 的差异、超时和重试；
- 在外部系统暂时失败或不可用时，尽量避免通知丢失；
- 用足够简单的架构完成可运行、可测试、可解释的第一版；
- 明确 MVP 的边界，避免把作业扩展成完整消息平台。

本文档同时作为作业实现的验收基线。最终仓库除了本文档和代码，还必须提供：

- 面向本项目的 README：说明问题理解、架构、启动方式、API 调用示例和测试方式；
- 可在本机运行的 MVP 实现；
- 一份基于真实过程填写的 AI 使用说明，而不是仅保留本文档末尾的模板。

本文档中的“必须”表示 MVP 验收要求；“建议”表示实现时可采用但不作为最低验收条件；“后续”表示明确不属于本次作业范围。

## 2. 背景与问题定义

企业内部多个业务系统会在注册成功、付款成功、下单等关键事件发生后，调用外部供应商的 HTTP(S) API。不同供应商在地址、Header、认证方式和 Body 格式上存在差异，而业务系统只关心“通知已经交给内部服务”，不应被外部 API 的返回值和可用性拖慢或耦合。

MVP 采用“调用方提交目标请求，服务负责可靠投递”的简化模型：`provider` 是供应商标识，`target` 中的 URL、Method、Headers 和 JSON Body 由受信任的内部调用方提交。服务不在 MVP 中维护供应商管理后台，也不负责把领域事件转换成供应商协议。供应商凭据不得硬编码或提交到 Git；生产部署应通过环境变量、本地密钥文件或域名白名单等方式注入和约束。

系统需要解决的核心问题是：

1. 接收业务方提交的通知任务；
2. 持久化任务，使进程重启后仍可恢复；
3. 按任务中的目标请求和供应商标识构造并发送 HTTP(S) 请求；
4. 对可重试失败进行有限次数的固定间隔重试；
5. 保存投递状态和失败原因，便于查询和人工处理。

## 3. 目标与非目标

### 3.1 目标

- 提供内部 API 创建通知任务；
- 支持自定义目标 URL、Method、Headers 和 JSON Body；
- 采用至少一次投递语义；
- 任务先持久化，再异步投递；
- 支持超时、有限重试和固定间隔退避；
- 支持按任务 ID 查询投递状态；
- 处理进程重启、Worker 崩溃和任务租约过期；
- 记录结构化日志和基础指标；
- 通过单元测试和集成测试验证核心行为。

### 3.2 非目标

MVP 不负责：

- 保证严格一次投递。HTTP 请求可能已经到达供应商但响应丢失，服务无法证明请求是否被处理；
- 解析所有供应商的业务响应并执行业务补偿；
- 实现通用工作流编排、事务消息或跨系统分布式事务；
- 提供复杂的供应商管理后台；
- 实现多区域容灾、跨地域复制和自动容量管理；
- 提供面向公网的开放平台能力；
- 替代业务系统的领域事件总线。

这些能力会显著增加部署、运维和一致性复杂度，不属于第一版证明核心投递链路所必需的范围。

## 4. 设计原则

1. **先落库，后投递**：API 返回成功的前提是通知任务已经持久化。
2. **至少一次优先**：宁可重复投递，也不因响应丢失而静默丢失通知。
3. **下游幂等**：每个任务提供稳定的通知 ID，并通过请求头传递给下游；下游应使用该 ID 去重。
4. **失败可见**：每个最终失败任务都保留状态、错误分类、重试次数和最后错误信息。
5. **MVP 控制复杂度**：用关系型数据库任务表和 Worker 完成调度，暂不引入消息队列。

## 5. 总体架构

```text
业务系统
    |
    | POST /v1/notifications
    v
通知 API 服务
    |
    | 事务写入
    v
notifications 数据表
    ^
    | 租约领取 / 状态更新
    |
投递 Worker -----> 外部供应商 HTTP(S) API
    |
    +----> 结构化日志、指标
```

### 5.1 组件职责

#### API 服务

- 校验请求格式和字段约束；
- 生成通知 ID；
- 将通知任务写入数据库；
- 返回任务已接收的结果；
- 提供状态查询接口。

API 服务不直接等待外部供应商响应，因此不会把供应商延迟暴露给业务系统。

#### 数据库

保存通知任务的完整输入、状态、重试信息和时间信息。数据库是 MVP 的可靠性基础，也是 Worker 之间共享任务状态的唯一事实来源。

#### 投递 Worker

- 定期查找待处理或到达重试时间的任务；
- 通过短租约领取任务，避免多个 Worker 同时处理同一任务；
- 构造 HTTP 请求并执行；
- 根据结果更新成功、重试或最终失败状态。

## 6. 任务状态机

```text
PENDING -> DELIVERING -> DELIVERED
    |          |
    |          +------> RETRY_WAITING -> DELIVERING
    |          |
    |          +------> FAILED
    |
    +------> RETRY_WAITING
```

状态定义：

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 已落库，等待首次投递 |
| `DELIVERING` | 已被 Worker 领取，正在投递 |
| `RETRY_WAITING` | 本次失败但仍可重试，等待下一次执行时间 |
| `DELIVERED` | 收到被定义为成功的 HTTP 响应 |
| `FAILED` | 超过最大重试次数，或发生不可重试错误 |

`DELIVERING` 状态必须带有租约过期时间。Worker 崩溃或机器断电后，其他 Worker 可以将租约已过期的任务重新置为可执行状态，从而避免任务永久卡住。

## 7. 投递语义与幂等性

### 7.1 投递语义

系统采用**至少一次投递**：只要任务没有被确认成功，就可能再次发送。

原因是 HTTP 请求存在以下不可判定场景：请求可能已经到达供应商，但服务在读取响应前崩溃。此时重试可能产生重复请求，而不重试则可能丢失通知。对于通知类场景，通常应优先选择不丢失，并要求供应商支持幂等。

### 7.2 幂等键

每个任务生成唯一 `notification_id`，并在下游请求中加入：

```text
Idempotency-Key: <notification_id>
X-Notification-ID: <notification_id>
```

服务本身只保证任务 ID 唯一，不声称能够替供应商完成去重。供应商不支持幂等时，设计文档必须明确重复通知风险。

## 8. API 设计

### 8.1 创建通知

```http
POST /v1/notifications
Content-Type: application/json
Authorization: Bearer <internal-token>
```

请求示例：

```json
{
  "provider": "crm",
  "event_type": "payment.succeeded",
  "target": {
    "url": "https://vendor.example.com/hooks/payment",
    "method": "POST",
    "headers": {
      "Authorization": "Bearer vendor-token",
      "Content-Type": "application/json"
    },
    "body": {
      "user_id": "u_123",
      "payment_id": "p_456",
      "status": "paid"
    }
  },
  "idempotency_key": "payment:p_456:crm"
}
```

成功响应：

```http
202 Accepted
```

```json
{
  "notification_id": "ntf_01H...",
  "status": "PENDING"
}
```

接口返回 `202` 只表示任务已经被服务接受并持久化，不表示外部供应商已经收到通知。

### 8.2 查询通知

```http
GET /v1/notifications/{notification_id}
```

响应至少包含：

- `notification_id`；
- `status`；
- `attempt_count`；
- `next_attempt_at`；
- `last_error_code`；
- `created_at`；
- `updated_at`；
- `delivered_at`。

### 8.3 请求校验

- 仅允许 `http` 和 `https` URL；
- 限制 URL、Header、Body 和总请求大小；
- `method` 默认使用 `POST`，MVP 可只支持 `POST`；
- 禁止客户端覆盖系统生成的幂等 Header；
- 客户端提交的 Header 仅用于本次任务；MVP 不把 Header 自动提升为全局供应商配置；
- `provider` 必须是非空、长度受限的标识，用于查询、日志和后续供应商级配置演进，不承担协议转换职责；
- 生产环境必须限制内部调用方身份；
- 应对 SSRF 风险进行网络出口限制或目标地址白名单控制。

### 8.4 API 行为契约

MVP 的 API 行为固定如下，便于业务方和测试用例依赖稳定契约：

| 场景 | HTTP 状态 | 说明 |
| --- | --- | --- |
| 请求格式正确且成功落库 | `202 Accepted` | 返回 `notification_id` 和 `PENDING` |
| JSON、字段类型或必填字段错误 | `400 Bad Request` | 不创建任务 |
| Token 或签名校验失败 | `401 Unauthorized` / `403 Forbidden` | 不创建任务 |
| URL、Header、Body 超限或违反安全策略 | `422 Unprocessable Entity` | 不创建任务 |
| 数据库不可用或事务提交失败 | `500 Internal Server Error` | 不返回任务 ID，不应伪装成已接受 |
| 查询不存在的任务 | `404 Not Found` | 不泄漏其他任务信息 |

创建接口必须在事务提交后才返回成功响应。响应体中的时间统一使用 UTC 的 RFC 3339 格式；状态枚举使用本文档定义的大写值。

当 `idempotency_key` 不为空时，接口按 `(provider, idempotency_key)` 做调用方幂等：首次请求创建任务，后续相同请求返回原任务 ID 和当前状态。若同一幂等键对应的请求内容不同，返回 `409 Conflict`，避免静默复用错误任务。MVP 可以通过请求内容摘要判断是否相同，摘要至少覆盖目标 URL、Method、Headers 和 Body。

## 9. 数据模型

核心表 `notifications` 包含：

| 字段 | 说明 |
| --- | --- |
| `id` | 通知 ID，主键 |
| `provider` | 供应商标识 |
| `event_type` | 业务事件类型 |
| `target_url` | 目标地址 |
| `http_method` | HTTP 方法 |
| `headers_json` | 请求 Header，敏感值应脱敏展示 |
| `body_json` | 请求 Body |
| `idempotency_key` | 业务幂等键，可为空 |
| `status` | 当前状态 |
| `attempt_count` | 已尝试次数 |
| `max_attempts` | 最大尝试次数 |
| `next_attempt_at` | 下一次可执行时间 |
| `lease_until` | 当前处理租约过期时间 |
| `last_error_code` | 最后一次错误分类 |
| `last_error_message` | 脱敏后的错误摘要 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `delivered_at` | 成功时间，可为空 |

MVP 支持调用方幂等，应对 `(provider, idempotency_key)` 建立唯一约束，并在重复提交时返回原通知 ID。

### 9.1 约束与索引

实现至少应建立以下数据库约束和索引：

- `status` 只能取本文档定义的五种状态；
- `attempt_count >= 0` 且 `max_attempts >= 1`；
- `lease_until` 仅在 `DELIVERING` 时有值，其他状态应为空；
- `delivered_at` 仅在 `DELIVERED` 时有值；
- `(status, next_attempt_at, created_at)` 联合索引，服务轮询使用；
- `(status, lease_until)` 联合索引，服务恢复过期租约使用；
- `provider, idempotency_key` 唯一索引；当数据库不支持空值唯一语义时，使用部分索引或把空键单独处理。

时间字段由服务端生成并统一使用 UTC。`headers_json` 和 `body_json` 使用数据库原生 JSON 类型；如果选用不支持 JSON 的数据库，必须在 Repository 层完成序列化和反序列化，不改变 API 的 JSON 契约。

### 9.2 状态更新不变量

所有状态更新都必须带上当前状态和任务 ID 条件，避免迟到的 Worker 覆盖新结果。例如投递完成只能执行 `WHERE id = ? AND status = 'DELIVERING'`；租约恢复只能执行 `WHERE id = ? AND status = 'DELIVERING' AND lease_until < now`。更新影响行数为 0 时，Worker 放弃本次写回并记录冲突，不得强行覆盖。

## 10. Worker 投递流程

1. 查询状态为 `PENDING` 或 `RETRY_WAITING` 且 `next_attempt_at <= now` 的任务；
2. 通过条件更新将任务改为 `DELIVERING`，同时写入 `lease_until`；
3. 构造请求，加入系统生成的通知 ID Header；
4. 使用连接超时和整体请求超时；
5. 根据响应状态或网络错误分类；
6. 成功则更新为 `DELIVERED`；
7. 可重试失败则增加 `attempt_count` 并更新为 `RETRY_WAITING`；
8. 不可重试失败或达到最大次数则更新为 `FAILED`；
9. 释放或清理租约。

任务领取必须是原子的。典型实现可以使用数据库事务、行锁或带条件的 `UPDATE`，避免两个 Worker 同时领取同一任务。

### 10.1 推荐的数据库领取流程

MVP 不要求批量领取或数据库特定锁语法。Worker 每次只领取一条任务，使用带条件的更新保证同一任务不会被重复领取：

1. 查询一条状态为 `PENDING` 或 `RETRY_WAITING` 且已到执行时间的任务；
2. 执行 `UPDATE ... WHERE id = ? AND status IN (...)`，将任务改为 `DELIVERING` 并写入 `lease_until`；
3. 只有更新影响行数为 1 的 Worker 才继续处理；
4. 提交更新后执行 HTTP 请求。

MVP 只运行一个 Worker 进程时，该机制已经足够；即使误启动多个 Worker，也不会因为同一条条件更新而同时处理同一任务。

### 10.2 Worker 循环与租约恢复

Worker 每隔 `poll_interval` 领取任务；每次领取前把 `DELIVERING AND lease_until < now` 的任务重新置为 `RETRY_WAITING`，并保留原有 `attempt_count`。恢复更新使用任务 ID 和租约时间条件，避免覆盖仍在有效租约内的任务。

建议默认值为 `poll_interval=1s`、`lease_duration=30s`。租约必须大于单次 HTTP 总超时；MVP 不实现租约续期。

Worker 收到停止信号后停止领取新任务；当前请求中断时依靠租约恢复。无论 HTTP 请求成功、失败还是客户端异常，都必须尝试写回状态，不能删除任务。

### 10.3 HTTP 请求边界

- 设置单次 HTTP 请求超时，默认 10 秒；MVP 不实现连接池调优和续租。
- 默认不跟随重定向，响应 Body 不需要保存，只记录状态码和错误类型。
- HTTP `2xx` 视为成功；其他状态按第 11 节分类。

## 11. 失败分类与重试策略

### 11.1 可重试错误

- DNS、连接建立、连接重置等网络错误；
- 请求超时；
- HTTP `408`、`425`、`429`；
- HTTP `500`、`502`、`503`、`504`；
- 供应商明确表示临时不可用的错误。

### 11.2 不可重试错误

- URL 或请求格式校验失败；
- HTTP `400`、`401`、`403`、`404`、`422`；
- Body 永久不符合供应商协议；
- SSRF 或安全策略拒绝；
- 超过最大尝试次数。

### 11.3 退避参数

MVP 默认：

- 最大尝试次数：5 次；
- 固定重试等待：每次重试等待 10 秒；
- MVP 不实现随机抖动和 `Retry-After` 解析。

最大尝试次数和等待时间通过配置注入即可，不需要单独的调度组件。

### 11.4 重试计数定义

`attempt_count` 表示已经发起过的 HTTP 请求次数。首次投递前为 `0`；本次请求视为第 `attempt_count + 1` 次。对于可重试失败，仅当 `attempt_count + 1 < max_attempts` 时进入 `RETRY_WAITING`，否则直接进入 `FAILED`。

失败后如果尚未达到 `max_attempts`，将 `next_attempt_at` 设置为当前时间加 10 秒；否则进入 `FAILED`。`next_attempt_at` 必须持久化，不能只保存在 Worker 内存中。

## 12. 安全与数据保护

- API 仅供内部系统调用，至少实现服务间 Token 或签名校验；
- 日志中不得输出 Authorization、Cookie、完整 Body 和其他敏感信息；
- 凭据通过环境变量或本地配置注入，不提交到 Git；
- 目标 URL 只允许 `http` 和 `https`，MVP 可通过供应商域名白名单降低 SSRF 风险；
- 设置请求 Body 大小和 HTTP 超时上限；
- 不保存供应商响应 Body。

### 12.1 SSRF 校验流程

创建任务时校验目标 URL，Worker 发起请求前再次检查 scheme。MVP 至少执行以下规则：

1. scheme 只能是 `http` 或 `https`；
2. URL 必须包含主机名，不允许用户名和密码；
3. 如果配置了供应商域名白名单，目标主机必须匹配白名单。

IP 段校验、DNS rebinding 防护和复杂出口网络控制属于后续增强项，不作为本次 MVP 的实现要求。

### 12.2 凭据处理

MVP 可接受配置中直接提供供应商 Header，但凭据必须放在环境变量或本地密钥文件中，不提交到 Git。日志和查询响应不得输出 `Authorization`、`Cookie`、`X-API-Key` 等敏感 Header；数据库加密和独立凭据服务留待后续版本。

## 13. 可观测性

### 13.1 日志

每次任务状态变化至少记录：

- `notification_id`；
- `provider`；
- `event_type`；
- `attempt_count`；
- `status`；
- `error_code`；
- 请求耗时。

不得记录未经脱敏的认证信息和请求 Body。

### 13.2 指标

MVP 只需提供以下基础指标或等价日志统计：

- 创建任务数量；
- 投递成功数量；
- 最终失败数量；
- 当前待处理任务数。

Prometheus、分布式追踪和供应商维度的复杂监控不属于 MVP 要求。

## 14. 一致性、恢复与运维行为

- 创建接口只有在数据库事务提交成功后才返回 `202`；
- Worker 领取任务后崩溃，租约到期后任务可再次执行；
- 服务重启不应丢失已落库任务；
- 启动时不需要扫描所有历史任务，只需依赖带索引的状态和时间字段查询；
- `FAILED` 任务保留在数据库中，MVP 可通过管理脚本或后续管理接口触发人工重试；
- 数据库不可用时，创建接口返回明确的 5xx，不应假装接受任务。

## 15. 技术选型与替代方案

### 15.1 MVP 选型

- HTTP API：选择团队熟悉的 Web 框架；
- 数据库：PostgreSQL 或 MySQL；
- Worker：同一应用中的后台进程或独立 Worker 进程；
- HTTP 客户端：支持连接超时、整体超时和响应状态读取的标准客户端；
- 本地开发：Docker Compose 启动数据库和服务。

选择关系型数据库任务表而不是消息队列，原因是：

- MVP 依赖更少；
- 状态、重试和查询可以放在同一个数据模型中；
- 本地运行和测试更简单；
- 能清晰展示至少一次投递和租约恢复机制。

### 15.2 替代方案

当任务量增大或数据库轮询成为瓶颈时，可以引入消息队列：API 负责写入任务记录并发布消息，Worker 消费消息并更新状态。此时仍需要处理消息重复、确认丢失、死信和状态对账，因此 MQ 不能自动消除至少一次语义下的幂等问题。

### 15.3 配置项

实现应提供可复制的 `.env.example`，至少包含：

| 配置 | 默认值 | 作用 |
| --- | --- | --- |
| `DATABASE_URL` | 无默认值 | 数据库连接串，缺失时拒绝启动 |
| `INTERNAL_AUTH_TOKEN` | 无默认值 | 内部 API 认证凭据 |
| `WORKER_ENABLED` | `true` | 是否启动当前进程内 Worker |
| `POLL_INTERVAL` | `1s` | 轮询间隔 |
| `LEASE_DURATION` | `30s` | 任务租约时长 |
| `REQUEST_TIMEOUT` | `10s` | 单次 HTTP 总超时 |
| `MAX_ATTEMPTS` | `5` | 默认最大尝试次数 |
| `RETRY_DELAY` | `10s` | 固定重试等待时间 |
| `MAX_REQUEST_BYTES` | `1048576` | 请求总大小上限 |

启动时必须校验配置格式和互相约束，例如 `LEASE_DURATION > REQUEST_TIMEOUT`、`MAX_ATTEMPTS >= 1`、超时和退避值为正数。配置错误应在启动阶段快速失败。

### 15.4 推荐代码边界

即使 API 和 Worker 部署在同一进程，也应按以下职责拆分，避免 HTTP 逻辑和状态机互相耦合：

```text
internal/
  api/           请求解析、认证、响应映射
  notification/  状态、重试和任务服务
  repository/    数据库读写和任务领取
  worker/        轮询、租约和 HTTP 投递
```

具体语言和 Web 框架可以由实现者选择。MVP 不要求拆分成多个服务或引入独立调度框架；上述目录只是为了保持 API、数据库和 Worker 逻辑可测试。

## 16. 容量与演进路线

### 第一阶段：作业 MVP

- 单体 API 和 Worker；
- 单数据库；
- 固定重试策略；
- 基础状态查询；
- 基础日志和指标。

### 第二阶段：水平扩展

- API 与 Worker 独立部署；
- 多 Worker 并发处理；
- 使用索引和批量领取优化轮询；
- 增加限流、供应商级并发上限和熔断；
- 引入死信队列或失败任务管理界面。

### 第三阶段：高吞吐和复杂调度

- 使用消息队列承载待投递任务；
- 使用分区表或归档策略控制数据库规模；
- 供应商配置中心和凭据管理；
- 分区域部署和灾备；
- 更完整的审计、追踪和告警体系。

## 17. 测试要求

### 17.1 单元测试

- 请求参数校验；
- 错误分类；
- 退避时间计算；
- 状态迁移合法性；
- Header 注入和敏感信息脱敏。

### 17.2 集成测试

- 创建任务后能够查询到 `PENDING`；
- Worker 能成功投递并变为 `DELIVERED`；
- 供应商返回 5xx 时进入重试；
- 达到最大次数后变为 `FAILED`；
- Worker 中途崩溃后租约到期，任务能再次执行；
- 进程重启后已落库任务不会丢失；
- 相同幂等键不会创建重复任务。

### 17.3 测试替身与验收数据

集成测试使用本地测试供应商 HTTP Server，不依赖真实第三方服务。测试 Server 至少支持按请求次数返回指定序列，例如 `[503, 503, 200]`，并记录收到的 Header、Body 和请求次数。数据库测试使用项目选定数据库的测试实例；如果为了作业简化，也可以使用 SQLite，但必须保留真实的持久化和状态更新行为。

最低测试矩阵如下：

| 用例 | 关键断言 |
| --- | --- |
| 首次创建 | 事务提交后返回 `202`，数据库状态为 `PENDING` |
| 相同幂等键 | 返回相同 `notification_id`，数据库只有一行 |
| 相同幂等键但内容不同 | 返回 `409`，原任务不变 |
| 供应商 `200` | 请求含两个系统幂等 Header，状态为 `DELIVERED` |
| 供应商 `503, 503, 200` | 状态经历 `RETRY_WAITING`，最终 `DELIVERED`，次数为 3 |
| 供应商 `400` | 不重试，状态为 `FAILED` |
| Worker 崩溃 | 租约到期后任务可再次领取 |
| 数据库不可用 | 创建接口返回 5xx，不返回成功任务 ID |
| URL 校验 | 非 HTTP(S) scheme 和不在白名单的域名被拒绝 |

### 17.4 本地运行与交付检查

仓库应提供一条清晰的本地启动路径，推荐包含：

1. `docker compose up -d db` 启动数据库；
2. `make migrate` 或等价命令创建表和索引；
3. `make run-api` 启动 API；
4. `make run-worker` 启动 Worker；
5. `make test` 执行单元测试和集成测试。

README 至少给出环境变量准备、迁移、启动、创建通知、查询状态和运行测试的示例。验收时应能用测试供应商在本机复现成功、重试、最终失败和租约恢复，而不需要外部账号。

### 17.5 验收标准

一个可接受的 MVP 至少应满足：

1. 能启动 API 和 Worker；
2. 能创建并持久化通知任务；
3. 能异步调用测试供应商；
4. 能展示成功、重试和最终失败状态；
5. 能通过测试证明重启和租约恢复不会静默丢弃任务；
6. README 能解释系统边界、投递语义、取舍和 AI 使用情况。

## 20. 关键取舍总结

本设计优先保证“任务不因服务重启或临时网络故障而轻易丢失”，因此接受重复投递的可能性，并通过通知 ID 和下游幂等降低重复影响。MVP 使用关系型数据库和 Worker，牺牲部分吞吐和实时调度能力，换取更低的部署复杂度、更清晰的状态模型和更容易验证的可靠性行为。
